# Проверка приложенного архива базы данных

Проверены файлы из `files (1).zip` и сопоставлены с текущей архитектурой `ku-portal` и онлайн-экзамена из `test-center-updated.zip`.

## Вывод

Архив содержит прототип отдельной SQLite → MySQL базы (`db.js`, `db_mysql.js`, `mysql_schema.js`, `migrate_to_mysql.js`). Он не является базой действующего KU Portal: в нём нет файла `school.db`, схемы пользователей и результатов портала, актуальных данных аккаунтов или резервной копии данных Alwaysdata. Текущий сайт использует постоянный закрытый каталог `KU_DATA_DIR`: `db.json`, `exam-sync.json`, `results.json` и другие файлы, описанные в `BACKEND.md`.

Подключать эти модули к действующему серверу без отдельной разработки и миграции нельзя: они не реализуют операции текущих модулей портала и экзамена.

## Обнаруженные проблемы

- `mysql_schema.js` первым делом выполняет `DROP TABLE` для пяти таблиц. `migrate_to_mysql.js` запускает этот список автоматически, поэтому повторный запуск удалит имеющиеся MySQL-таблицы и их данные.
- Перенос читает только SQLite `school.db`, которого в предоставленном архиве нет. Скрипт не создаёт резервную копию целевой MySQL базы и не делает весь перенос одной транзакцией.
- Контроль переноса сверяет только число строк и сумму баллов в `results`; остальные таблицы и содержимое не сверяются. Сравнение `a.n === b.n` может также дать ложное несовпадение из-за разных типов числа и значения из SQLite.
- Модули MySQL меняют API функций на асинхронный (`await`) и требуют `mysql2`; это несовместимо с текущими синхронными SQLite вызовами без переделки всех вызывающих участков.
- В автономном архиве экзамена логины и общие пароли находятся в клиентском HTML/JS, а локальная проверка пароля выполняется в браузере. Этот вариант не подходит для рабочего сайта.

## Совместимость онлайн-экзамена

`exam-sync/base-exams.json` из архива совпадает с версией в текущем репозитории. Защищённая серверная реализация сайта уже содержит эти базовые экзамены и их актуальную модель. Остальные `handler.js`, `index.html` и `seed.json` из архива относятся к старой автономной схеме. Их прямое копирование удалило бы серверную авторизацию и защиту ответов; миграция старого обработчика очищает экзамены, публикации и связанные работы при переходе схемы.

## Текущее местоположение данных Alwaysdata

В рабочем checkout репозитория производственные базы и копии отсутствуют. Руководство проекта указывает закрытый путь `~/ku-portal/data/` или значение `KU_DATA_DIR` из настроек процесса сайта. На FileZilla данные можно просматривать через SFTP в этом каталоге, но точный путь нужно сверить с переменной `KU_DATA_DIR` в настройках сайта Alwaysdata. Каталог `data/` является закрытым: не переносите его в `www` и не публикуйте файлы баз.

## Ограничение списка аккаунтов

`account-types.csv` перечисляет типы и права, предусмотренные кодом. Полный перечень фактических пользователей, их групп, текущих прав и экзаменационных аккаунтов хранится только в закрытых данных Alwaysdata; его нет ни в GitHub, ни в приложенных архивах. Архивные 4 преподавателя и 72 студента не подтверждают, что такие аккаунты созданы на рабочем сайте.
